规范驱动 开发 先规范，后编码
AI 写代码又快又多，但「写得快」不等于「写得对」。SDD 的做法是：动手编码前先产出一份人可评审的规范，批准后才进入开发 —— 把人的把关点从「读代码」前移到「读文档」。

THE PROBLEM
CONTEXT

生产代码的速度，远超人审查代码的速度

01
从意图到代码的「跳跃」
复杂变更里有大量设计决策（接口契约、数据迁移、失败处理、兼容性）。全由智能体即兴决定，人只能事后从几百行 diff 反推 —— 纠错成本已经很高。
02
评审代码贵，评审文档便宜
读 500 行 PR 要极强专注力还常看不出设计问题；读一页「改什么行为、边界在哪、怎么验证」的文档只要几分钟。把关点越靠前，纠错成本越低。
03
vibe coding 缺可追溯依据
一句话 prompt 生成大量代码，事后没人说得清「当时约定的行为是什么」，设计意图散落在聊天记录里。
04
自动化开发需要质量闸
允许智能体自主开发时，风险不是「改错一行」，而是「沿错误方向做完整件事」。流水线需要机制保证：进入开发的每个任务，方案都经人确认。
CONTEXT
0208
THE DEFINITION
THREE RULES

三条核心约定

Spec is Truth
①
先规范，后编码
每个开发任务动手前先产出规范文档，说清可观察的行为变化、边界、关键决策和验证方式。
②
人工批准是进入开发的闸门
规范必须经人评审批准，未批准的任务不能开始编码 —— 无论手工启动还是自动化编排。
③
规范是唯一事实来源（Spec is Truth）
开发以规范为准；发现规范有误或需偏离时，不是悄悄绕开，而是先改规范（反向同步 Reverse Sync），让文档与代码始终一致。

0408
THE VALUE
BENEFITS

为什么值得多走一轮

1
把关点前移
纠错成本最低
方向错误在文档阶段被发现，改一段话；代码阶段发现，改一个 PR；上线后发现，改一次事故。
2
评审不需要读代码
一份好规范让评审者不读代码库也能判断批准还是驳回 —— 这正是「AI 执行、人把关」分工成立的前提。
3
决策有据可查
规范记录行为约定、边界与取舍，与意图、会话、分支串成完整链路，可追溯、可审计。
4
代码与文档不漂移
「唯一事实来源 + 反向同步」从机制上保证文档跟着实现走，不会合并后就过期。
5
自动化的安全带
有了「规范已批准」这个可检查门禁，自主开发循环（拾取 → 开发 → 提交）才敢真正放手运转。
BENEFITS
0508
WHEN TO USE
SCOPE

SDD 是质量闸，闸门有成本 —— 按风险权衡

✅ 适合开启
  • 涉及接口契约 / 持久化数据 / 迁移 / 安全 / 跨模块影响 —— 错了很难回头
  • 多人协作项目 —— 规范是团队对「做成什么样」的共识载体
  • 用自动化编排让智能体自主开发 —— 人不在场，闸门是唯一把关点
  • 对可追溯性有要求（审计、合规、长期维护）
⛔ 可以不开
  • 小修小补（改文案、补校验）—— 意图的 Acceptance 已够把关
  • 实验性探索（spike、原型）—— 方案本身就是探索目标
  • 个人小项目快速迭代 —— 人自己就在回路里，闸门收益有限
在 c3 中，SDD 是工作区级开关 —— 同一个 c3 里，重要项目开、实验项目关，互不影响。

IN c3
WORKFLOW

从意图到合并，四步走完

①
编写规范
写入受限的规范会话产出 spec.md，可反复细化 / 重置重写。
→
②
批准规范
人工检查点：在规范文档页点击批准（记录批准人；生成后 10 秒内不可批准）。
→
③
开始工作
服务端强制校验「规范已批准」才启动开发会话，以 spec 为唯一事实来源。
→
④
开发完成
标准开发循环：提交 / PR → 标记 done。
四态主按钮：todo 意图主按钮按状态呈现 —— 无规范 ⇒ 编写规范；已写未批准 ⇒ 批准规范；已批准 ⇒ 开始工作。②是核心人工检查点，③的门禁在服务端强制，不靠前端隐藏按钮。
