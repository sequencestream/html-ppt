## 第 01 页 · 封面 / 钩子

- **Tagline**：c3 GUIDE / SPEC-DRIVEN DEVELOPMENT
- **主标题**：
  - 规范驱动开发
  - **先规范，后编码**（橙色强调）
- **脚注**：AI 写代码又快又多，但「写得快」不等于「写得对」。SDD 的做法是：动手编码前，先产出一份**人可评审的规范**，批准后才进入开发——把人的把关点从「读代码」前移到「读文档」。
- **右侧视觉锚点**：一道「闸门（Gate）」——规范未批准，闸门不开。
- **页脚**：c3 GUIDE · SDD ｜ 01 · 08

**讲解要点**：先抛出反差——AI 让编码不再是瓶颈，新瓶颈是「人审查代码的速度跟不上 AI 生产代码的速度」。SDD 就是补这道缺口。

## 第 02 页 · 背景 · AI 编码时代的新失衡

- **Topbar**：THE PROBLEM ｜ 徽标 CONTEXT
- **标题**：生产代码的速度，远超人审查代码的速度
- **副文**：智能体成为执行主体后，出现了传统软件工程没有的失衡。四个具体表现：
- **四顽疾（卡片 / stat grid）**：

  | # | 症结 | 说明 |
  |---|------|------|
  | 1 | 从意图到代码的「跳跃」 | 复杂变更里有大量设计决策（接口契约、数据迁移、失败处理、兼容性）。全由智能体即兴决定，人只能事后从几百行 diff 反推——纠错成本已经很高。 |
  | 2 | 评审代码贵，评审文档便宜 | 读 500 行 PR 要极强专注力还常看不出设计问题；读一页「改什么行为、边界在哪、怎么验证」的文档只要几分钟。**把关点越靠前，纠错成本越低。** |
  | 3 | vibe coding 缺可追溯依据 | 一句话 prompt 生成大量代码，事后没人说得清「当时约定的行为是什么」，设计意图散落在聊天记录里。 |
  | 4 | 自动化开发需要质量闸 | 允许智能体自主开发时，风险不是「改错一行」，而是「沿错误方向做完整件事」。流水线需要机制保证：进入开发的每个任务，方案都经人确认。 |

- **页脚**：CONTEXT ｜ 02 · 08

**讲解要点**：这四点是 SDD 存在的理由，逐条点破「为什么光有意图还不够」。

## 第 03 页 · 定义 · SDD 是什么（三条核心约定）

- **Topbar**：THE DEFINITION ｜ 徽标 THREE RULES
- **标题**：规范驱动开发的三条约定
- **三条约定（竖排大条）**：

  | 约定 | 内容 |
  |------|------|
  | **① 先规范，后编码** | 每个开发任务动手前先产出规范文档，说清可观察的行为变化、边界、关键决策和验证方式。 |
  | **② 人工批准是进入开发的闸门** | 规范必须经人评审批准，未批准的任务不能开始编码——无论手工启动还是自动化编排。 |
  | **③ 规范是唯一事实来源（Spec is Truth）** | 开发以规范为准；发现规范有误或需偏离时，不是悄悄绕开，而是**先改规范（反向同步 Reverse Sync）**，让文档与代码始终一致。 |

- **印章**：Spec is Truth
- **页脚**：THREE RULES ｜ 03 · 08

**讲解要点**：三条是 SDD 的骨架。强调第③条——规范不是写完就丢的一次性文档，它跟着实现走。

## 第 04 页 · 定义 · 开发智能体的工作契约

- **Topbar**：THE CONTRACT ｜ 徽标 WORKING CONTRACT
- **标题**：SDD 模式下，开发智能体遵循的六条契约
- **六契约网格**：

  | 契约 | 含义 |
  |------|------|
  | **Spec is Truth** | 以规范为准 |
  | **Restate First** | 动手前先复述理解 |
  | **Checkpoint Before Execute** | 关键节点先过检查点 |
  | **Done by Evidence** | 以证据判定完成，而非自我宣告 |
  | **Reverse Sync** | 实现与规范分歧时，反向同步规范 |
  | **Ask for Clarification** | 有歧义就提问而不是猜 |

- **金句条**：
  > 意图是「要做什么」的契约，规范是「具体做成什么样」的契约。
- **页脚**：WORKING CONTRACT ｜ 04 · 08

**讲解要点**：这六条把抽象的「以规范为准」变成智能体可执行的行为准则，是「AI 执行、人把关」得以成立的运行时保证。

## 第 05 页 · 价值 · SDD 的五个好处

- **Topbar**：THE VALUE ｜ 徽标 BENEFITS
- **标题**：为什么值得多走一轮
- **五好处（编号条）**：

  | # | 好处 | 说明 |
  |---|------|------|
  | 1 | 把关点前移，纠错成本最低 | 方向错误在文档阶段被发现，改一段话；代码阶段发现，改一个 PR；上线后发现，改一次事故。 |
  | 2 | 评审不需要读代码 | 一份好规范让评审者不读代码库也能判断批准还是驳回——这正是「AI 执行、人把关」分工成立的前提。 |
  | 3 | 决策有据可查 | 规范记录行为约定、边界与取舍，与意图、会话、分支串成完整链路，可追溯、可审计。 |
  | 4 | 代码与文档不漂移 | 「唯一事实来源 + 反向同步」从机制上保证文档跟着实现走，不会合并后就过期。 |
  | 5 | 自动化的安全带 | 有了「规范已批准」这个可检查门禁，自主开发循环（拾取 → 开发 → 提交）才敢真正放手运转。 |

- **页脚**：BENEFITS ｜ 05 · 08

**讲解要点**：好处 1 是核心逻辑，好处 5 承接第 06、08 页的自动化叙事。

## 第 06 页 · 价值 · 什么时候该开 SDD

- **Topbar**：WHEN TO USE ｜ 徽标 SCOPE
- **标题**：SDD 是质量闸，闸门有成本——按风险权衡
- **副文**：SDD **不是越多越好**（多一轮撰写和评审），按项目和变更的风险取舍。
- **左右对比两栏**：

  | ✅ 适合开启 | ⛔ 可以不开 |
  |------------|------------|
  | 涉及**接口契约 / 持久化数据 / 迁移 / 安全 / 跨模块影响**——错了很难回头 | 小修小补（改文案、补校验）——意图的 Acceptance 已够把关 |
  | **多人协作**项目——规范是团队对「做成什么样」的共识载体 | 实验性探索（spike、原型）——方案本身就是探索目标 |
  | 用**自动化编排**让智能体自主开发——人不在场，闸门是唯一把关点 | 个人小项目快速迭代——人自己就在回路里，闸门收益有限 |
  | 对可追溯性有要求（审计、合规、长期维护） | |

- **补注**：在 c3 中，SDD 是**工作区级开关**——同一个 c3 里，重要项目开、实验项目关，互不影响。
- **页脚**：SCOPE ｜ 06 · 08

**讲解要点**：破除「开了 SDD 就要处处写规范」的顾虑——它是可按项目权衡的开关。

## 第 07 页 · 落地 · c3 中的 SDD 四步流程

- **Topbar**：IN c3 ｜ 徽标 WORKFLOW
- **标题**：从意图到合并，四步走完
- **流水线图（横向四段 + 闸门）**：

  ```
  意图（todo）
     │
     ▼
  ① 编写规范  ──► 写入受限的规范会话产出 spec.md（可反复细化 / 重置重写）
     │
     ▼
  ② 批准规范  ──► 人工检查点：在规范文档页点击批准（记录批准人；生成后 10 秒内不可批准）
     │
     ▼
  ③ 开始工作  ──► 服务端强制校验「规范已批准」才启动开发会话，以 spec 为唯一事实来源
     │
     ▼
  ④ 开发完成 → 提交 / PR → 标记 done
  ```

- **四态主按钮说明**：`todo` 意图主按钮按状态呈现——无规范 ⇒ **编写规范**；已写未批准 ⇒ **批准规范**；已批准 ⇒ **开始工作**。
- **页脚**：WORKFLOW ｜ 07 · 08

**讲解要点**：这是操作主线。强调②是 SDD 的核心人工检查点，③的门禁在服务端强制，不靠前端隐藏按钮。
