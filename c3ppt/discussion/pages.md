## 第 01 页 · 封面 / 钩子

- **Tagline**：c3 GUIDE / AGENT DISCUSSION
- **主标题**：
  - 从人开会
  - 到 **Agent 讨论**（橙色强调）
- **脚注**：把一群人拉进会议室讨论出结论，正在演变为**让一组 AI 智能体围绕你的目标进行圆桌研讨**。人负责定方向、做判断；阅读代码、检索资料、独立发言交给 agent。
- **右侧视觉锚点**：一张「圆桌」——多个智能体席位环绕，其中一席是人。
- **页脚**：c3 GUIDE · DISCUSSION ｜ 01 · 08

**讲解要点**：开场抛出转变——在 AI 软件工程时代，「把相关的人拉进会议室」这个前提正在瓦解，因为项目背后可能只剩一位人类工程师加一队智能体。

## 第 02 页 · 背景 · 传统开会的五顽疾

- **Topbar**：THE PROBLEM ｜ 徽标 CONTEXT
- **标题**：会议本身没错，错的是它积累的一系列顽疾
- **副文**：软件团队解决「方向不明的问题」靠开会——头脑风暴、方案评审、技术选型、复盘。但实践中它有五个老毛病：
- **五顽疾（卡片 / stat grid）**：

  | # | 症结 | 说明 |
  |---|------|------|
  | 1 | 组织成本高，质量看运气 | 凑齐合适的人要协调日程、往往等好几天；到场的人未必做了功课，「现场现想」质量参差；缺了关键领域知识就注定开不出结果。 |
  | 2 | 发言不均衡，声音大的人主导 | 职级高、嗓门大、先发言的人天然占优；深思熟虑但表达慢的人常说不完；「共识」很多时候只是「没人再反驳」。 |
  | 3 | 过程丢失，结论模糊 | 大多数会议没有完整记录。哪些方案被否掉、为什么、结论的前提是什么——散落在白板和记忆里，几周后没人说得清。 |
  | 4 | 讨论与执行脱节 | 结论躺在纪要里，还要有人翻译成需求、拆成任务。这道「翻译」既是延迟也是失真——执行的人往往只拿到一句结论。 |
  | 5 | 会议室里可能只剩一个人 | 「开会」默认背后是一群人；但当项目由一位工程师带一队智能体驱动，你没法把 agent 请进会议室，也不该让唯一的人替所有视角发言。 |

- **页脚**：CONTEXT ｜ 02 · 08

**讲解要点**：前四条是传统会议的顽疾，第五条是根本性的前提瓦解——它引出「需要一种人与 agent、agent 与 agent 平等研讨的新形态」。

## 第 03 页 · 定义 · Agent 讨论是什么

- **Topbar**：THE DEFINITION ｜ 徽标 WHAT IT IS
- **标题**：多智能体、多轮、圆桌研讨，收敛出结构化结论
- **副文**：不是简单「问一个 AI」，而是刻意引入**多个独立视角**。五个关键设计：
- **五设计（编号条）**：

  | # | 设计 | 内容 |
  |---|------|------|
  | 1 | 每个参与者独立作答 | 同一问题并行发给多个智能体，各自基于同样的讨论记录独立表达——不存在「先发言的人带偏全场」。 |
  | 2 | 主持人负责组织与收敛 | 主持人把目标拆成子议题、逐个推进、归纳观点、向各方确认、写下结论——发散和收敛都有明确机制。 |
  | 3 | 讨论前先做功课 | 只读研究智能体先读代码、检索资料，把事实、现状、约束整理好——所有人带着同一份背景材料入场。 |
  | 4 | 人随时可以介入 | 你可以旁观、暂停、插话、追问，但不必全程在场；完整发言记录和结论随时回看。 |
  | 5 | 结论直通执行 | 结论可一键转化为意图（Intent），进入「确认 → 开发 → 验收」，不再需要人工翻译。 |

- **金句条**：
  > 传统会议靠「凑人 + 抢话 + 纪要」；Agent 讨论是「随叫随到的多视角圆桌，全程留痕，结论直接接入开发」。
- **页脚**：WHAT IT IS ｜ 03 · 08

**讲解要点**：这五点正好逐条回应第 02 页的五顽疾——独立作答对治发言不均衡，全程留痕对治过程丢失，结论直通对治执行脱节。

## 第 04 页 · 场景 · 五种讨论类型 & 何时不用

- **Topbar**：WHEN TO USE ｜ 徽标 SCENARIOS
- **标题**：方向不明、需要多视角碰撞时，才开讨论
- **五类型（表格 / 卡片）**：

  | 场景 | 讨论类型 | 典型问题 |
  |------|---------|---------|
  | 头脑风暴 | **Brainstorm** | 「缓存层有哪些可行的演进方向？」——先发散再收敛 |
  | 方案决策 | **Decision** | 「消息队列选 Kafka 还是 NATS？」——按标准对比、选一个并说明理由 |
  | 评审把关 | **Review** | 「这份 API 设计稿有什么问题？」——多视角暴露风险 |
  | 计划拆解 | **Planning** | 「下个季度的重构怎么排？」——拆成有序执行计划 |
  | 复盘总结 | **Retro** | 「这次线上事故暴露了什么？」——梳理发生了什么、为什么、下次改什么 |

- **反面提示条（右侧 / 底部）**：
  > **目标已清晰、只差动手**的事不需要讨论——直接创建意图或在会话里开工。
  > 判断标准：能一句话说清「做什么、怎么算做完」就不必开；说出口的是「我拿不准…」「有没有更好的…」，那才是讨论的用武之地。
- **页脚**：SCENARIOS ｜ 04 · 08

**讲解要点**：五种类型决定各阶段的引导方式。强调最后的判断标准——讨论是为「拿不准」而生，别把它用在已经明确的小事上。

## 第 05 页 · 价值 · 从人开会转向 Agent 讨论的好处

- **Topbar**：THE VALUE ｜ 徽标 BENEFITS
- **标题**：为什么值得从会议室搬到圆桌
- **五好处（编号条）**：

  | # | 好处 | 说明 |
  |---|------|------|
  | 1 | 零协调成本，随时可开 | 不用约时间、不用等人，想法冒出来就发起，几分钟拿到多视角结论。 |
  | 2 | 视角天然多元且均衡 | 参与者可以是不同厂商、不同配置的智能体，独立发言、机会均等——没有职级压制和会议室政治。 |
  | 3 | 过程全程留痕 | 每轮谁说了什么、议题如何推进、结论如何得出，完整记录随时回看——结论不再是无源之水。 |
  | 4 | 人在关键处把关 | 不必全程盯着：中途插话纠偏、结论不满意时追问续跑，把精力花在「提好问题、判断好坏」。 |
  | 5 | 结论无缝接入执行 | 一键转意图，讨论积累的背景、研究、权衡随之进入意图细化——从「聊出方向」到「开始开发」没有断层。 |

- **页脚**：BENEFITS ｜ 05 · 08

**讲解要点**：好处逐条对照第 02 页顽疾闭环——零协调对治组织成本高，多元均衡对治声音大主导，全程留痕对治过程丢失，无缝接入对治讨论执行脱节。

## 第 06 页 · 落地 · c3 中讨论的构成与三种角色

- **Topbar**：IN c3 ｜ 徽标 ANATOMY
- **标题**：讨论负责「想清楚」，意图负责「做出来」
- **左栏 · 讨论的构成（结构化记录字段）**：

  | 字段 | 说明 |
  |------|------|
  | 类型 type | Brainstorm / Decision / Review / Planning / Retro |
  | 目标 goal | 要回答的问题，标题由它派生 |
  | 上下文 context | 你提供的背景，作为原始输入永久保留 |
  | 研究结果 researchResult | 只读研究智能体产出的现状调研，与上下文分开存放 |
  | 主持人 organizer / 参与者 participants | 组织者 + 智能体集合（可混合厂商） |
  | 议程 agenda / 结论 conclusion | 有序子议题 → 最终产出（可转意图） |
  | 状态 status | `draft` → `in_progress` → `completed` / `cancelled` |

- **右栏 · 三种角色**：
  - **主持人 Organizer**：每轮决策——拆议程、提名发言、广播问题、归纳小结、推进阶段、写结论。即使只有它一个也能「单人深思」。
  - **参与者 Participant**：被提名或广播时独立发言，只补新观点、不重复；视角差异来自不同模型与配置。
  - **人 Human**：随时暂停、插话、追问；你的发言进入记录，主持人下一轮就读到。
- **页脚**：ANATOMY ｜ 06 · 08

**讲解要点**：一句话定位——讨论想清楚、意图做出来，二者打通。强调主持人「优雅退化为单人深思」，即使只有一个智能体也能跑。

## 第 07 页 · 落地 · 生命周期与人的三种介入

- **Topbar**：THE FLOW ｜ 徽标 LIFECYCLE
- **标题**：只读研究先行，四阶段单向推进，一定会结束
- **生命周期图（横向流水线）**：

  ```
  创建 draft
     │
     ▼
  只读研究 ──► 只读智能体读代码 / 检索资料，只产出「事实·现状·约束·待澄清」，不给方案（避免污染）
     │
     ▼
  自动开始 in_progress
     │
     ▼
  发散 discuss（广播并行） → 归纳 summarize（提名串行） → 确认 confirm → 结论 conclude
     │
     ▼
  完成 completed → [可选] 转化为意图 / 继续追问
  ```

- **三个「一定」（要点条）**：
  - **发散靠广播，收敛靠提名**：发散阶段同一子问题并行广播，互不干扰；归纳/确认逐个提名，串行打磨。
  - **阶段只进不退**：四阶段单向推进，保证一定会收敛。
  - **一定会结束**：每阶段轮次上限（默认 12）+ 整场硬上限（默认 40），触顶写兜底结论，不会无限烧钱。
- **人的三种介入（小卡片）**：
  - **暂停 / 恢复**（进行中）：在轮次边界挂起，恢复后原地继续。
  - **发言**（进行中）：插话进入记录，主持人下轮据此调整。
  - **继续**（已完成）：不满意就追问，在完整记录之上续跑、产出新结论。
- **页脚**：LIFECYCLE ｜ 07 · 08

**讲解要点**：操作主线。强调「只读研究刻意不给方案」和「阶段只进不退 + 双重轮次上限」——这两点保证讨论既客观又一定收敛。结论完成后可一键转意图，接入「意图 → 开发」路径。

## 第 08 页 · 收尾 / 行动号召

- **Topbar**：END OF DECK ｜ 徽标 FIN.
- **大字标题**：随叫随到的多视角圆桌
- **Strap**：
  <mark>拿不准方向的大问题，用讨论；方向明确的小事，直接开工。</mark>
  发起后去做别的事，回来看结论；觉得偏了再用「继续」追问一轮——往往比中途干预更省心。
- **印章**：c3 · Agent Discussion
- **页脚**：c3 GUIDE · DISCUSSION ｜ 08 · 08

**讲解要点**：收束到「零协调、多视角、全程留痕、结论直通执行」的核心价值，呼应第 02 页顽疾与第 05 页好处，形成闭环。
